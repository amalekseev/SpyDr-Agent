## 1. Что такое auto-spydr

**auto-spydr** — платформа для автоматической конвертации ручных тест-кейсов в Gherkin-сценарии (`.feature` файлы) с помощью LLM-агента.

Система решает одну из главных болей QA-команд: ручные тесты написаны в произвольном текстовом формате, а для запуска в pytest-bdd нужны структурированные `.feature` файлы с шагами в строго определённом каталоге. Переписывать вручную — долго и дорого. auto-spydr делает это автоматически через интерактивный чат-агент.

### Ключевые понятия

- **BDD-шаги (steps)** — это готовые, реализованные функции в вашем pytest-bdd проекте. Каждый шаг имеет паттерн вида `пользователь открыл страницу "{url}"`. Агент может использовать только их — он не придумывает шаги сам.
- **Каталог шагов** — набор всех доступных шагов, автоматически извлекаемых из Python-исходников pytest-bdd через AST-парсинг. Система сканирует директорию со step-определениями (настраивается через `steps_dir` в конфиге) и строит индекс.
- **RAG (Retrieval-Augmented Generation)** — технология семантического поиска по каталогу шагов через pgvector. Агент находит шаги по смыслу, а не по точному тексту.
- **Few-shots** — эталонные примеры готовых `.feature` файлов, которые агент использует как образцы при составлении плана.
- **Feature-файл** — результат работы агента: файл формата Gherkin (`.feature`), который напрямую запускается pytest-bdd.

## 2. Архитектура системы

```
                    ┌─────────────────────────────────────────┐
                    │              PostgreSQL + pgvector        │
                    │  ┌──────────┐  ┌──────────┐  ┌────────┐ │
                    │  │bdd_steps │  │few_shots │  │project_│ │
                    │  │(шаги)    │  │(примеры) │  │docs    │ │
                    └──┴──────────┴──┴──────────┴──┴────────┘─┘
                              ▲              ▲
                    ┌─────────┴──────────────┴───────┐
                    │          LLM (GigaChat)         │
                    └─────────────────────────────────┘
                              ▲
                              │
                    ┌─────────▼─────────┐
                    │   SpyDR Agent      │
                    │   (Streamlit)      │
                    │   интерактивно     │
                    └────────────────────┘
```

**Поток данных (интерактивный режим):**
1. Пользователь вводит запрос в чат
2. Агент вызывает `create_plan` — планировщик с few-shots и документацией
3. Агент вызывает `search_steps` — семантический поиск шагов по pgvector
4. Агент вызывает инструменты сборки (`set_feature_meta`, `add_scenario`, `add_step` и т.д.)
5. `.feature` файл отображается в реальном времени в боковой панели

## 3. Установка и первый запуск

### Требования

- Python 3.11+
- Доступ к **pgvector**

### Установка зависимостей

```bash
pip install -r requirements.txt
```

### Первый запуск: последовательность шагов

```
1. Задать CONNECTION_STRING в .env (строка подключения к PostgreSQL)
2. Настроить steps_dir в src/configs/config.yml (путь к директории со step-определениями)
3. Проиндексировать шаги в pgvector: python -m src.scripts.index_steps
4. (Опционально) Проиндексировать документацию: python -m src.scripts.index_docs
5. (Опционально) Подготовить few-shots индекс: python -m src.scripts.generate_few_shots_index
                                                 python -m src.scripts.index_few_shots
6. Запустить агента: streamlit run src/api/streamlit_app.py
```

## 4. Переменные окружения

В файле `.env` (или через `export` / в конфиге CI) задаётся **единственная** переменная окружения:

```bash
CONNECTION_STRING="postgresql://postgres:mypassword@localhost:5488/postgres"
```

> **Важно:** `CONNECTION_STRING` используется и интерактивным агентом, и скриптами индексации. Переменная должна быть задана до запуска любого компонента системы.

## 5. Конфигурационные файлы

В проекте два конфигурационных файла с разными зонами ответственности.

---

### `src/agents/config.yml` — конфигурация LLM-агента

Этот файл управляет тем, какую модель использует **интерактивный агент SpyDR**.

```yaml
llm_params:
  provider: gigachat
  model: GigaChat-2-Max     # Название модели
  temperature: 0            # 0 = детерминированные ответы
  cert_file: /path/to/client.crt       # mTLS-сертификат клиента
  key_file: /path/to/client.key        # Приватный ключ клиента
  # key_file_password: "..."           # Опционально: пароль к ключу

validation:
  max_iterations: 3         # Максимум попыток автоисправления feature
  llm_params:
    provider: gigachat
    model: GigaChat-2-Max   # Модель валидатора (может отличаться от основной)
    temperature: 0
    cert_file: /path/to/client.crt
    key_file: /path/to/client.key
```

> При использовании провайдера `gigachat` необходимо указать пути к mTLS-сертификатам (`cert_file`, `key_file`) в секции `llm_params`. Если модель валидатора тоже GigaChat — сертификаты нужны и в `validation.llm_params`.

**Параметр `validation.max_iterations`** — максимальное количество итераций автоматической валидации и исправления сгенерированного feature. При включённой валидации в UI агент после генерации проверяет результат отдельной LLM и при нахождении ошибок пытается их исправить. Если за `max_iterations` попыток ошибки не устранены — feature возвращается как есть.

---

### `src/configs/config.yml` — глобальная конфигурация RAG

Этот файл управляет векторными коллекциями, эмбеддингами и дополнительными возможностями.

```yaml
steps_dir: gherkin/tests/steps          # Путь к директории со step-определениями pytest-bdd

rag:
  provider: gigachat                    # Провайдер эмбеддингов
  params:
    model: GigaChat-2-Max               # Модель эмбеддингов
    cert_file: /path/to/client.crt      # mTLS-сертификат (при использовании GigaChat)
    key_file: /path/to/client.key       # Приватный ключ (при использовании GigaChat)

  steps:
    collection_name: bdd_steps          # Имя коллекции шагов в pgvector
    top_k: 8                            # Сколько шагов возвращать при поиске

  docs:
    collection_name: project_docs     # Коллекция документации проекта
    path: docs                        # Папка с документами (.pdf, .docx, .txt)
    top_k: 5                          # Топ-K фрагментов документации
    chunk_size: 1000                  # Размер чанка при нарезке документов
    chunk_overlap: 200                # Перекрытие между чанками

  few_shots:
    collection_name: few_shots        # Коллекция few-shot примеров
    top_k: 3                          # Количество примеров для подбора
    index_path: src/configs/few_shots_index.json
    few_shots_dir: few_shots          # Папка с эталонными .feature файлами
    batch_size: 100

docstring:
  supported_langs:                    # Языки для валидации docstring в шагах
    - python
    - json
    - xml
    - sql
```

**Важные параметры:**

| Параметр | Что меняет |
|----------|------------|
| `steps_dir` | Путь к директории с Python-файлами step-определений pytest-bdd. Система парсит их через AST и строит каталог шагов. Может быть абсолютным или относительным (от корня проекта) |
| `rag.provider` + `rag.params.model` | Модель эмбеддингов для **всего** RAG (шаги, документы, few-shots). Должна совпадать с тем, чем проводилась индексация |
| `rag.params.cert_file` / `rag.params.key_file` | Пути к mTLS-сертификатам. Обязательны при `provider: gigachat` |
| `rag.steps.top_k` | Сколько кандидатов-шагов агент видит за один поиск. Увеличьте, если агент часто не находит нужный шаг |
| `rag.docs.path` | Путь к папке с документацией проекта. Документы из этой папки попадают в системный промпт агента |
| `docstring.supported_langs` | Языки, которые агент обязан указывать в `docstring_lang` при добавлении шагов с docstring-содержимым |

> **Критически важно:** если вы меняете `rag.provider` или `rag.params.model` — необходимо переиндексировать **все** коллекции (шаги, документацию, few-shots), т.к. эмбеддинги старой модели несовместимы с новой.

## 6. Файл правил RULES.md

`RULES.md` — пользовательский файл правил, который агент читает при каждом старте и добавляет в свой системный промпт.

Здесь вы можете прописать:
- Соглашения о наименованиях сценариев и feature
- Обязательные теги для определённых типов тестов
- Запрет на использование определённых шагов
- Любые доменные правила вашего проекта

**Пример содержимого:**

```markdown
- Все feature файлы должны иметь тег @regression
- Сценарии для API тестов должны иметь тег @api
- Названия сценариев пишутся в повелительном наклонении
- Не использовать шаги с прямым SQL-доступом в smoke-тестах
```

Файл читается автоматически — редактируйте и перезапускайте приложение, чтобы изменения вступили в силу.

## 7. Интерактивный агент SpyDR (Streamlit-чат)

### Запуск

```bash
streamlit run src/api/streamlit_app.py
```

Откройте браузер: [http://localhost:8501](http://localhost:8501)

### Интерфейс

Приложение состоит из двух зон:

**Основная область (центр)** — чат с агентом:
- Поле ввода внизу: опишите, какой feature-файл вам нужен
- История переписки с агентом отображается выше
- Агент показывает статусы своих действий в процессе работы (`⏳ Ищу шаги по N запросам…`)

**Боковая панель (sidebar)** — живой предпросмотр feature:
- Секция **Feature** — отображает актуальное содержимое `.feature` файла в реальном времени по мере работы агента
- Кнопка **Скачать .feature** — появляется после генерации, позволяет сохранить результат
- Секция **Валидация**:
  - Тоггл «Валидация feature» — включает автоматическую проверку и исправление после генерации
  - «Макс. итераций» — количество попыток автоисправления (активно только при включённой валидации)
- Секция **Сессия**:
  - Кнопка «Очистить чат» — сбрасывает историю диалога и начинает новую сессию
- **Выбор проекта** — если в конфиге настроены несколько проектов с разными каталогами шагов, здесь можно переключаться между ними. При смене проекта сессия сбрасывается автоматически.

### Как общаться с агентом

Агент понимает описания на русском языке в произвольной форме. Чем подробнее вы опишете нужный тест, тем точнее будет результат.

**Примеры запросов:**

```
Создай feature для тестирования авторизации пользователя.
Нужно: сценарий входа с верными данными, сценарий входа с неверным паролем,
сценарий блокировки после 3 неудачных попыток.
```

```
Сгенерируй feature для API-теста создания заказа.
POST /api/orders, в теле передаётся JSON с полями product_id и quantity.
Проверь: успешное создание (201), ошибку при отсутствующем товаре (404),
ошибку валидации при отрицательном quantity (400).
```

**Итеративная доработка в рамках сессии:**

После получения первого варианта вы можете продолжать диалог:

```
Добавь в Background шаг авторизации — он нужен во всех сценариях.
```

```
В третьем сценарии убери шаг проверки email и замени его проверкой статуса.
```

```
Добавь тег @smoke к первому сценарию.
```

### Что делает агент «под капотом»

При получении запроса агент выполняет строго последовательную цепочку инструментов:

1. `create_plan` — вызывает отдельную LLM-планировщик, которая изучает запрос, подбирает похожие few-shot примеры из `few_shots/` и составляет детальный план сборки
2. `set_feature_meta` — задаёт название и теги feature
3. `add_background_step` — добавляет общие шаги в Background (если нужно)
4. `add_scenario` — создаёт каждый сценарий
5. `search_steps` — ищет подходящие шаги в pgvector по семантике
6. `add_step` — добавляет найденные шаги в сценарии (с валидацией параметров)
7. `show_state` — проверяет итоговое состояние

Если включена валидация — после сборки запускается дополнительная LLM-проверка; при нахождении ошибок агент пытается их исправить.

### Валидация feature

Включите тоггл «Валидация feature» в боковой панели перед отправкой запроса.

Валидатор проверяет:
- Соответствие сгенерированного feature исходному запросу
- Полноту покрытия всех указанных в запросе сценариев
- Корректность структуры

При нахождении проблем агент получает детальный фидбек и пересобирает проблемные части. Процесс повторяется до `max_iterations` раз.

## 8. Индексация: когда и как переиндексировать

Индексация — это загрузка данных в векторную БД (pgvector) с созданием эмбеддингов. Без неё RAG-поиск не работает.

### Три независимые коллекции

| Коллекция | Данные | Имя в pgvector |
|-----------|--------|----------------|
| **Шаги** | BDD-шаги из pytest-bdd исходников | `bdd_steps` |
| **Документация** | Файлы из папки `docs/` (.pdf, .docx, .txt) | `project_docs` |
| **Few-shots** | Эталонные `.feature` примеры из `few_shots/` | `few_shots` |

---

### Когда переиндексировать шаги (`bdd_steps`)

Переиндексация шагов нужна, когда **изменились step-определения**:

- ✅ Изменены, добавлены или удалены Python-файлы в директории `steps_dir`
- ✅ Первый запуск системы
- ✅ Смена провайдера или модели эмбеддингов

**Как переиндексировать:**

```bash
python -m src.scripts.index_steps
```

**Флаги index_steps:**

```bash
# Пропустить если данные уже есть (безопасный вариант для CI)
python -m src.scripts.index_steps --check

# Переиндексировать шаги для конкретного проекта
python -m src.scripts.index_steps --project my_project

# Переиндексировать шаги для всех проектов
python -m src.scripts.index_steps --all-projects
```

---

### Когда переиндексировать документацию (`project_docs`)

Переиндексация документации нужна, когда **изменились файлы в папке `docs/`**:

- ✅ Добавлены новые документы (.pdf, .docx, .txt)
- ✅ Обновлено содержимое существующих документов
- ✅ Смена модели эмбеддингов
- ✅ Первый запуск с документацией

```bash
python -m src.scripts.index_docs
```

Поддерживаемые форматы: `.pdf`, `.docx`, `.txt`

> После переиндексации документации также рекомендуется обновить суммаризации для системного промпта:
> ```bash
> python -m src.scripts.generate_docs_summary
> ```

---

### Когда переиндексировать few-shots (`few_shots`)

Переиндексация few-shots нужна, когда **изменились эталонные примеры в `few_shots/`**:

- ✅ Добавлены новые эталонные `.feature` файлы
- ✅ Удалены или изменены существующие примеры
- ✅ Смена модели эмбеддингов
- ✅ Первый запуск

```bash
# Шаг 1: сгенерировать индекс (hook-описания через LLM)
python -m src.scripts.generate_few_shots_index

# Только для новых файлов, не трогая уже проиндексированные:
python -m src.scripts.generate_few_shots_index --merge

# Шаг 2: загрузить в pgvector
python -m src.scripts.index_few_shots
```

---

### Полная переиндексация при смене модели эмбеддингов

Если вы меняете `rag.provider` или `rag.params.model` в `src/configs/config.yml` — **обязательно** переиндексируйте всё:

```bash
# 1. Переиндексировать шаги
python -m src.scripts.index_steps

# 2. Переиндексировать документацию
python -m src.scripts.index_docs
python -m src.scripts.generate_docs_summary

# 3. Переиндексировать few-shots
python -m src.scripts.generate_few_shots_index
python -m src.scripts.index_few_shots
```

## 9. Скрипты в папке `src/scripts/`

Это внутренние скрипты системы для подготовки данных. Запускаются как Python-модули (`python -m src.scripts.<name>`).

---

### `src/scripts/index_steps.py`

Парсинг step-определений из Python-исходников и индексация в pgvector.

```bash
python -m src.scripts.index_steps                        # полная переиндексация
python -m src.scripts.index_steps --check                # пропустить если данные есть
python -m src.scripts.index_steps --project my_project   # шаги для одного проекта
python -m src.scripts.index_steps --all-projects         # шаги для всех проектов
```

---

### `src/scripts/index_docs.py`

Индексация документации из папки `docs/` в pgvector (`project_docs`).

```bash
python -m src.scripts.index_docs
```

Поддерживает: `.pdf`, `.docx`, `.txt`. Документы нарезаются на чанки (размер задаётся в `src/configs/config.yml`).

---

### `src/scripts/index_few_shots.py`

Индексация few-shot примеров в pgvector (`few_shots`). Требует предварительного запуска `generate_few_shots_index`.

```bash
python -m src.scripts.index_few_shots
```

---

### `src/scripts/generate_few_shots_index.py`

Генерация файла `src/configs/few_shots_index.json` через LLM. Для каждого `.feature` файла в папке `few_shots/` LLM составляет короткое описание (hook) на русском языке — оно потом используется для эмбеддинг-поиска подходящих примеров.

```bash
python -m src.scripts.generate_few_shots_index           # полная перегенерация
python -m src.scripts.generate_few_shots_index --merge   # только новые файлы
python -m src.scripts.generate_few_shots_index --dry-run # посмотреть что будет обработано
```

---

### `src/scripts/generate_docs_summary.py`

Генерация суммаризирующих артефактов из документации в `docs/`. Результаты сохраняются в `src/agents/prompts/` и добавляются в системный промпт агента.

```bash
python -m src.scripts.generate_docs_summary          # оба файла
python -m src.scripts.generate_docs_summary --hooks  # только docs_hooks.md (RAG-хуки)
python -m src.scripts.generate_docs_summary --summary # только docs_summary.md (саммари)
```

Генерирует два файла:
- `docs_hooks.md` — ключевые термины и паттерны из документации (для RAG-поиска)
- `docs_summary.md` — плотное резюме документации (для системного промпта)

**Когда запускать:** после любого обновления документации в `docs/`, а также после `index_docs`.

## 10. Типовые рабочие процессы

### Воркфлоу 1: Генерация feature-файла из ручного теста

Основной сценарий ежедневной работы с системой.

1. **Запустите агента** (если ещё не запущен):
   ```bash
   streamlit run src/api/streamlit_app.py
   ```
2. **Выберите проект** — если в системе настроено несколько проектов с разными каталогами шагов, выберите нужный в боковой панели.
3. **Настройте валидацию** — при необходимости включите тоггл «Валидация feature» в sidebar'е и задайте количество итераций. Рекомендуется для критичных тестов.
4. **Отправьте ручной тест в чат** — вставьте текст ручного тест-кейса или опишите, что нужно протестировать. Агент построит план, подберёт шаги и соберёт `.feature` файл.
5. **Проверьте результат** — в боковой панели отобразится сгенерированный feature. Оцените: все ли сценарии на месте, правильно ли подобраны шаги, корректны ли параметры.
6. **Доработайте в диалоге** — если что-то не так, напишите агенту, что исправить. Например: «Убери второй сценарий», «Замени шаг проверки на шаг с ожиданием». Агент внесёт правки в тот же feature.
7. **Скачайте готовый файл** — когда результат устраивает, нажмите «Скачать .feature» в sidebar'е.

> **Совет:** если вы замечаете, что одни и те же правки повторяются от теста к тесту (например, «всегда добавляй тег @regression» или «в Background всегда должен быть шаг авторизации»), — запишите их в `RULES.md`. Агент будет учитывать эти правила автоматически при каждой генерации, и вам больше не придётся просить об этом вручную.

> **Требования к few-shot примерам:**
>

## 12. Частые вопросы

### Агент не находит нужный шаг

**Причины и решения:**

1. Шаг не был проиндексирован → переиндексируйте: `python -m src.scripts.index_steps`
2. Шаг есть в каталоге, но поиск его не возвращает → увеличьте `top_k` в `src/configs/config.yml` (например, с 8 до 15)
3. Шаг действительно не существует в вашем pytest-bdd проекте → нужно добавить его реализацию в директорию `steps_dir` и переиндексировать

### Агент «придумывает» шаги, которых нет

Это противоречит правилам агента — он настроен использовать **только** шаги из каталога. Если такое происходит, проверьте:
- Корректность step-определений в `steps_dir` (убедитесь, что файлы актуальны)
- Актуальность индекса (переиндексируйте: `python -m src.scripts.index_steps`)

### После смены модели эмбеддингов поиск стал работать хуже

Необходима полная переиндексация. Старые векторы несовместимы с новой моделью. См. «Полная переиндексация при смене модели» в разделе 8.

### Streamlit-агент не запускается: ошибка подключения к БД

1. Убедитесь, что PostgreSQL запущен
2. Убедитесь, что `CONNECTION_STRING` задан корректно
3. Убедитесь, что расширение pgvector установлено в базе

### Как добавить поддержку нескольких проектов с разными каталогами шагов?

В `src/configs/config.yml` добавьте секцию `projects`:

```yaml
projects:
  project_a:
    custom_steps_dir: path/to/project_a/steps
  project_b:
    custom_steps_dir: path/to/project_b/steps
```

Затем проиндексируйте шаги для каждого проекта:

```bash
python -m src.scripts.index_steps --project project_a
python -m src.scripts.index_steps --project project_b
```

В интерфейсе агента появится выпадающий список выбора проекта.

### Качество генерации низкое — что улучшить?

1. **Добавьте документацию проекта** в `docs/` и переиндексируйте — агент будет лучше понимать контекст
2. **Добавьте few-shots** — положите 5–10 качественных примеров в `few_shots/` и переиндексируйте
3. **Уточните правила** в `RULES.md` — пропишите специфику вашего проекта
4. **Используйте более мощную модель** — смените `model` в `src/agents/config.yml`
5. **Включите валидацию** — тоггл в sidebar'е агента

### Как интерпретировать метрики Pass Rate?

Pass Rate — процент сценариев, которые **прошли** при запуске через pytest-bdd. Это жёсткая метрика: 0% если хотя бы один шаг не совпал с паттерном. Учитывайте, что:
- Сценарии с нереализованными шагами автоматически **исключаются** из запуска (не засчитываются как провальные)
- Высокий Pass Rate говорит о том, что агент подбирает реально существующие шаги
